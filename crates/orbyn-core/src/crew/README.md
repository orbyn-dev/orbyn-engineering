# Crew

Crew is Preview: the engine-agnostic crew of agents of [docs/crew.md](../../../../docs/crew.md),
behind `CoreConfig::crew_preview`, which ships `false` (`ORBYN_CREW_PREVIEW=1` turns it on for the service). With it off, no Crew tool is listed or
callable and nothing here runs. The protocol's objects are in `orbyn-contracts` and are stored
by `store::crew` ([Crew Protocol](../../../../docs/crew/protocol/SPEC.md)).

## What it owns

| Module | Owns |
| --- | --- |
| `router` | Router v0: filters, scores from seeded defaults, an explicit engine honoured and still checked, and the `RouteDecision`. Pure: no model, no process, no file |
| `filters` | The hard filters, in order, each rejection with its reason. `class_screen` runs first |
| `classes` | Data classes: `.orbyn/crew.json` read at the pinned base commit and at the default branch, the stricter applies (strict, fail closed), the last accepted default-branch ref and commit remembered per project with a person's confirm or reset, the glob, a brief's files against the classes, the `route_class` ledger row and the three read-only views |
| `score` | Pass rate for the brief's kind (seeded defaults until `EvalHistory` has a measured rate) and quota headroom, in permille |
| `tiers` | The tier a role needs; native model-family words and explicit exact ACP engine/model admission |
| `tier_settings` | Person-owned ACP assignments: revision saves plus reviewed-default preconditions; no tier guessing |
| `view` | A plain copy of one engine's status, models and usage |
| `gather` | Builds the views from the engine registry and model list the engine picker reads, and limits from the usage cache only |
| `stamp` | A brief draft becomes a brief: the core adds the envelope, a draft that carries one is refused |
| `draft` | The JSON Schema `crew_start` lists for its drafts, a valid example, and every problem in a bad draft at once |
| `guard` | The secret scan (H2) and the answer-key leak check (H1) |
| `persist` | Storing a decision with its task, after both checks |
| `tool` | The tool list and `crew_route`, the dry-run tool |
| `start` | `crew_start`: validates the brief and key, refuses a crew that spent its turn budget, routes, grants the leases and runs the worker through `delegate` |
| `worktree` | A writing worker's own checkout (issue #436): `<repo>-wt/crew-<member>` beside the clone on branch `crew-<member>`, made before its thread and removed when that start fails — a checkout that already existed is left alone, and one this start made is kept when its worker cannot be confirmed stopped. One folder per member, reused across that member's tasks; a folder a crash left and git no longer lists is cleared by the next start only when Orbyn's own record at `<repo>-wt/.orbyn/crew-<member>` says Orbyn made it and the folder is still this clone's checkout, and any other folder is kept with the start refused until a person moves or removes it. Off by default (`CoreConfig::crew_writer_worktrees`), because a start still reads the protected-file and index-flag baselines from the lead's checkout |
| `report` | `crew_report`: the worker's result, stamped by the core, then the verifier |
| `lifecycle` | The task states and transitions of SPEC.md section 6, and the loop guard. Pure |
| `leases` | Grants the brief's files to its worker; refuses protected paths, files outside the brief and a reviewer's write; reads expiry on use; refuses a worker's file change outside its lease at the gate, before the write |
| `checks` | The check runners: command kinds, `file_scope`, `diff_size`, `schema`, `secret_scan`, `repo_required`. Any other kind is `skipped` with the accepted limit it records (#793): what it needs and the decision it waits on |
| `http_probe` | The `http_probe` runner: one GET to the key's loopback URL, compared with its `expect_status`. No redirect followed and no retry; no answer is an error, never a pass |
| `verify` | The verifier: runs the key in the task's checkout, writes Evidence and the Gate, builds the reason a worker may read |
| `workers` | The allow list of Orbyn tools a Crew worker may call; every other `orbyn_*` tool, including any added later, is refused |
| `codex_homes` | A Codex crew task's private `CODEX_HOME`: made before its first turn with only an API-key `auth.json`, reused by its later turns, removed when the task ends and swept at core start when its task is not live |
| `protect` | Records the key's protected files (type, executable bit, SHA-256 of the exact bytes, links not followed) before the worker exists, and compares at verify time. Git is not asked, so nothing the worker can write in `.git` hides a change |
| `recover` | After a restart: clears dead verification claims, verifies a task left `verifying`, stops one whose worker is gone, sets the budget timers again |
| [`bus`](bus/README.md) | The Crew bus: `crew_post`, `crew_ask`, the board, steering delivery and the guards for hops, posts, sizes and the end of a run |
| [`autopilot`](autopilot/README.md) | Autopilot: the always-denied list, the approval chain, two keys, trip wires and the approval ledger |
| [`review`](review/README.md) | Review stages: reviewer lanes, typed findings, the finding check, the fix loop and repo rules that add lanes |
| `capacity` | Review capacity: the count of waiting High and Medium merges, whether a new Low-priority start that Crew began itself pauses over the limit (8), and the seeded random sample of a batch (off by default, one in four). The decisions are pure. `provenance` is the one part that runs git: it reads the merged range's new-file hunks (byte-exact `-U0` diff; binary, deleted and unsafe paths skipped), gives each line an author through `git blame` of the merge commit (the task's engine and model, or a person only for a line whose last-changing commit is in the positive `person_commits` list the caller passes; anything not positively a person's is the agent's, and an author email is never read; the merge hook must pass only positively identified person commits, never a guess) and writes a local-only note on the merge commit under `refs/notes/orbyn-agent-trace` (ids, ranges and counts, never content; a merge with no hunk has no note and no `note_ref`, so it reads as Not measured). `crew_provenance_start` is first-write-wins: an older merge recorded late reads as Not measured. Provenance and the coverage built on it are merge-level, not line-level review. The start hook (`capacity/hooks.rs`, flag-gated) runs before `crew_start` grants a worker and refuses a Low-priority start that Crew began itself over the limit with `not_authorized`, naming the waiting count and the limit. That refusal is never retried by a timer or a loop and is shown plainly as waiting: a merge-comment fix keeps its Comment stored and the merge's `needs_person` note says the fix waits for review capacity (answering again starts it, which clears the note); a review fix tells the lead the same, and since a confirmed finding is decided once, a new review of the work is its next trigger. Pausing is off until a person turns on `pause_enabled` (migration 50). A launch with `Links::crew_started` (review fixes, merge-comment fixes) is stored Low and Crew-started; every other start is Medium and person-started. `capacity/coverage.rs` and `capacity/api.rs` build the coverage map and the person-facing state. The merge hook (same file, flag-gated) runs after a merge row is stored, in a detached task with an EMPTY person-commit list: every line reads as the agent until a later change passes positively identified person commits. A failure is logged and written to the approval ledger on the merge's task as `provenance_failed` (stage, a fixed code-owned reason that never holds git output or a path, `coverage: Not measured`, `resolved: false`; the ledger write itself is tried three times), and never fails the merge. A failed merge has no note, so coverage reads it as Not measured. The next merge's hook first retries up to 10 unresolved failures, oldest first, recording each as of its own merge time (hunks are replaced, so a retry is safe); a success writes a `resolved: true` row on the same task. A repository whose provenance already began later than the failed merge still reads it as Not measured. Writes of `refs/notes/orbyn-agent-trace` are taken one at a time in this process, keyed by the shared git directory (so linked worktrees share the lock), and each git call is bounded at 30 s; a ref lock clash with another process is only tried again up to 5 times, with no cross-process guarantee. The `resolved: true` row keeps kind `provenance_failed` and has no `why` or `coverage`, so a generic ledger view lists it like a failure; read `resolved`. A retry pass takes the 10 oldest failures not yet retried 3 times; each failed retry writes a `retry_failed` row with `attempt`, and after the third the merge stays Not measured and is not retried again, so permanent failures cannot hold back newer ones. Sampling runs in the same detached task (`capacity/batch.rs`), only when a person set sampling to `one_in_four` (off by default; off reads the merge's project and its setting and writes nothing): a Low merge joins its project's open batch, the Low merges that landed since the last recorded batch, and the oldest four close first and again while four remain, so a merge is never skipped whatever order the hooks finish in (there is no digest in the app yet, so a short batch stays open). Low merges that landed before sampling was turned on are never sampled or recorded: the boundary is the time of the latest settings audit row that turned sampling on (`crew_sampling_since`, no migration), so turning it off and on again resets it, and saving other settings with sampling still on does not move it. One in four, rounded up, is picked at random with a seed from the system, not risk-weighted; High and Medium merges are never in a batch. Every task of the batch is recorded once in `crew_review_samples` with whether it was picked and the seed; the choice is never given to the worker and the merge row, review state and `needs_person` are not touched. `GET /api/crew/capacity` lists the picked tasks whose merge still waits as `picked`. A refused start is also noted as one bounded `crew_paused_starts` row (migration 54, `store/crew_paused_starts.rs`; ids, counts and times only, 200 per project, a repeat updates its row, the same trigger starting marks it `started`) and listed as `held` by `GET /api/crew/capacity`. Settings, a task's priority and the recorded samples are kept by `store/crew_capacity.rs` (migration 47), hunks and the first provenance time by `store/crew_provenance.rs` (migration 48) |
| `backtest` | Reviewer backtest, pure part (slice 4n PR 1): which pull requests are eligible (merged within 180 days, at least 30 days old), the `EscapeSource` trait for outcomes (the real source, `escape_log.rs`, reads the escape log: see below), and each lane's recall and precision from 5 escapes and 10 findings, matched by file only. `replay` (PR 2) is the one part that runs: `run` replays each requested review lane or check on each eligible pull request through a `LaneRunner` (fake in tests, no live engine yet), keeps a budget of tokens per engine that is never summed or pooled (a lane stops when its own engine's budget is spent; lanes of one engine share it), records a broken lane as failed without stopping the others, stores each finding fingerprint with `caught`, `unmatched` or `no_escape`, and scores with `score`. When the escape source says Not measured the run still finishes and shows finding counts only. A request is refused if it has a builder lane, a money-like field or name, or an engine without a budget. A person starts it: no timer, startup hook or scheduler calls it, and a test fails if any other non-test code reaches it. `api` (PR 3) is the person's way in, behind the Preview flag: `crew_backtest_estimate` and `crew_backtest_report` only read; `crew_backtest_start` records the run and replays it in the background, one run at a time (a second start is refused in the same transaction that would insert it), and is refused until a live `LaneRunner` exists (none yet: tests install a fake); `crew_backtest_stop` only asks, and the run ends as stopped before its next replay. Outcomes come from the escape log through `EscapeLog` (read-only): confirmed escapes only, merged in the 30 to 180 day window and found within 30 days of their merge; the pull request is the merge's record id and the files are those the escape's fix or revert commit changed, read from git on the merge's checkout; an escape whose files cannot be read (a post-merge check or a person's mark names no commit, no checkout, git failed) is counted as unresolved beside the lane's score and never scored; a log that cannot be read whole (over its 5,000 cap, one damaged row) or that holds no escape at all is Not measured, never partial. History is the project's own Crew merges, numbered by merge record. `crew_backtest_recover` runs once when the core opens and marks a run a crash left `running` as failed, "interrupted". Scoring normalises paths (`./`, `..`, separators) and counts identical findings once. Stored by `store/crew_backtest.rs` (migration 49, ids, counts and fingerprints only) |
| `escapes` | The escape log (slice 4k): reads (PR 1), a person's writes (PR 2, `person.rs`: mark, confirm, dismiss, gap; `Person` routes, audit first, `409 stale`, idempotent), a person's created check (PR 4, `check.rs`: propose, accept, approve, retry, withdraw; `Person` routes; only accept starts a worker, through the router; the worker may add exactly one test file (`check_paths.rs`); the proof (`check_proof.rs`) runs on a `git archive` tree, with output discarded and a time limit, confined on macOS and otherwise only after a person approves the exact change; it must fail on the escaped merge and pass on the fix; every task an accept created is recorded for good, and the merge queue's entries and `merge_blocker` refuse it unless the escape's current check names it, is `proven` and was proven on the commit being queued, through one shared guard; the tick unwinds stuck and withdrawn checks; migration 52) and the possible-escape scan (PR 3, `scan.rs`: three signals from read-only git on the project checkout, writes `possible` only, bounded, idempotent, run by the service's own tick; `possible.rs` reads `GET /escapes/possible`, which never writes). PR 1: merges that got past review and checks and were later found defective. A revert is a **possible** escape at once, written by the schema (migration 51 back-fills it and a trigger on `crew_merges` adds it with the revert); confirmed only when a person confirms or marks it (PR 2). Possible, confirmed and dismissed are always separate counts. Display only: the breaker, Router and gates never read it. Views for `GET /api/crew/escapes`, `/escapes/{id}`, `/escapes/thresholds` and `/escapes/counts` (`counts.rs`: one area's merges and escapes per engine in the log's window, possible/confirmed/dismissed apart and no rate, busiest first, at most `ESCAPE_COUNT_ENGINES_MAX` rows with `truncated` when more had a merge there, an unknown project and an area that is not a name refused; it decides no engine); thresholds (60 d, 14 d, 10 merges, 2x) are device config in `settings`. Stored by `store/crew_escapes.rs`, whose read functions are the stable API for the backtest's `EscapeSource`. See [docs/crew/escapes.md](../../../../docs/crew/escapes.md) |
| `background` | Background crews' state: definition, strict validation, redaction, runs with spend against a budget set at creation (the run's turns and minutes live on the run row as they are spent), and the stop for the budget that queues a review. Stored in the data folder, audited, no trigger and no engine. Its rows that wait for the person are joined to the Review queue by `autopilot/merge/review_queue` (read side, paged with the merges), and the person settles one with `background_acknowledge_review` (`POST /api/crew/background/runs/{id}/acknowledge`, a Person route): the wait clears, the crew reads nothing waiting, and the run keeps why it waited, its state, its stop reason and its spend. The `watch` trigger kind (slice A1) is stored too: a command of 1 to 500 characters, `every_hours` 1 to 720, `on_failing` `needs_you` or `template`, at most 10 watches per project, screened at create and update by the always-denied list and the blast-radius guard; the `watch` module runs one on its timer |
| `background_daily` | The daily per-engine budget (slice 4h, PR 2, migration 57): runs and turns each engine may spend on one crew in a day, fixed at creation with the person's UTC offset, so the day is theirs and the budget resets at their midnight. Turns are counted from the engine event (`crew_worker_run_ended`, one call per turn, whatever the turn did) and minutes are wall time, in `store::crew_background`'s ledger of one row per run, day and engine, so no engine's count can touch another's. No engine takes a hard limit: a run already going is cancelled at the cap, stopped `budget` and waiting for the person with what the engine spent shown, never clamped; a failed verification checks the cap before it retries (`settle_failure`). A new event whose engine has spent the day is refused before anything is stored, never held or queued, with an audit row `crew.background.daily.refused` reading "daily budget spent: <engine>" and a sentence with the time the day turns; the check sits before the capacity pause, in `launch_crew_task`. A turn of a run still running that cannot be counted (the crew or the worker's engine unreadable, or the ledger write failing) stops the run `budget` too; only a background run is ever stopped this way, and a late turn of an ended run is counted best effort without touching the run or its task. A budget that cannot be read fails closed: a start is refused and a run in flight is stopped `budget`, never allowed on. A turn that ends after its run did still counts for the engine's day. The person's offset is fixed at creation, so after a daylight-saving change the reset is an hour off their wall clock until the crew is made again. A crew made before the slice has no daily budget (0 and 0): nothing is counted for it and nothing is refused |
| `background_listeners` | The background events no person pressed (slice 4h, PR 3, migration 59): one owned future, `run_crew_background_listeners`, the service opts in behind the Preview flag with an interval (60s to 24h, `ORBYN_CREW_BACKGROUND_WATCH_INTERVAL_SECS`; no interval means no pass at all) and awaits on shutdown. Each pass fires what is due for crews that are on (a crew that is off is never read from the forge or the tracker and spends no event), at most one start per crew per pass, and watches at most 64 CI crews per pass from a rotating start (and reads at most 64 issue-label crews and separately 64 dependency-update crews per pass from the same rotating start, so a store full of crews cannot turn one pass into unbounded traffic): a `schedule` crew once per `every_hours` window, a `watch` crew's command once per `every_hours` window (its own tick, see `watch`), a `ci_failure` crew on a failed check run at its branch head (its setting, else the project default) narrowed by its optional workflow filter, and an `issue_label` crew on an open issue the project's one connected tracker reader reports with the crew's stored label (a project with no reader, or a tracker that cannot answer, spends no event; a crew's first pass per stored label baselines the one matching page it reads and starts nothing, and a claim keeps a hash of the issue's sorted label set, so an edit is inert and only a label-set change fires - a removal and re-add is not fired, a label feed is a reader follow-up, the baseline ignores the reader's next page, and re-enabling a crew does not baseline again, so labels added while it was off fire once per pass). A `dependency_update` crew reads its project's tracker: GitHub answers from its open Dependabot alerts (one page of 100), every other tracker answers cannot and spends no event, and a crew's first pass that gets a feed is a baseline (every update its optional `ecosystem` selects is claimed and nothing starts), so only a later unclaimed update starts one run; the `gh` scopes Dependabot alerts need are unconfirmed on a real machine; a `watch` crew's tick is its own (see `watch`). Every firing of the other listeners starts a run through the same seam as Run now (`crew_background_start`) with the event in the `PausedTrigger` key (`<crew>:schedule:<start>`, `<crew>:ci:<head>:<hash of the name>`, `<crew>:issue_label:<hash of scope>:<hash of key>:<hash of label>`, one event per head and failing check or per issue and label, as the design note says), and claims a first-write-wins event row (migration 59) first, so a repeat of the same event starts nothing new and a refused firing (a run already running, no engine, an untrusted folder, capacity, the daily budget) is never retried on a timer and writes one `crew.background.listener.refused` audit row. A schedule window start at or before the newest claimed one never fires, and a stop is checked between firings only, never inside a start. Event text from outside — a check's name, a head sha, a tracker issue's scope and key (kept raw only in the claim identity, hashed in the trigger key), a `.orbyn/crew.json` trigger's name — only selects what to start and reaches only a hash of the check's name in the dedupe key and the trigger key, and a diagnostic line; the brief stays code-owned (decision 6). A file trigger with no matching crew is ignored: nothing starts, nothing is adopted, at most the diagnostic line "found in .orbyn/crew.json, no matching crew", no UI. A watch's check is not a start: it starts a run only when a result turns failing with `on_failing` = `template`, so a baseline, an unchanged result or a failing turn set to `needs_you` starts no run and spends no run budget |
| `watch` | A watch's fixed command (KC6 slices 2 and 3): the runner (`watch_check`: screened again before every check, run in the project's checkout for at most five minutes through the checks' `run_line`, its output redacted and cut to the last 20 lines and at most 2 KiB) and the pure state machine (`plan`): the first check that runs is a baseline and raises nothing, only a pass<->fail turn is a change, a failing turn raises one Needs you row or starts the crew's template through `crew_background_start` (never a model call of its own), a passing turn resolves a raised row (a failing baseline or a started template recovers with action `none`), and three checks in a row that could not run raise one row until a check runs again; turning it off writes one `turned_off` change row. Reads `background_watch` and `background_watch_changes` (state, and the change history newest first, pages). Its rows are migration 77's `crew_watch_state` and `crew_watch_changes`; no migration was added |
| `background_start` | Run now (slice 4h, PR 1): a person starts one run of an enabled background crew by hand (the `manual` event, `Core::crew_background_run_now`). It makes the run's lead thread (the run's id is the thread's id, the `crew_id` of its tasks; no engine ever runs it and `tell_lead` skips it), stores no Autopilot mode row: a background run's merges are `off` in code, so every merge of the run waits for a person, and starts the task through `launch_crew_task` as Crew-started and Low priority, so `capacity_start_check` can pause it (the refusal is a held `background` start with key `<crew>:manual`, and the run and thread are taken back). The crew's turns and minutes are the brief's budget: minutes are the existing task timer, turns are the worker's runs, checked when a verification fails, and each turn is also counted on the run row as its engine event ends (PR 2, `background_daily`), so the run's live spend is real, not reconstructed. A background worker's turn with no output fails the run (`NO_REPLY`, engine error) instead of being judged by what it leaves behind. A task's end ends the run: passed is `needs_review`; budget, repeated failure and engine error are `stopped` with that reason; anything else is `needs_review` with a plain sentence. The brief is code-owned per template (no event or repository text in it) and may write under the repository's top-level entries except `.orbyn/` and `.github/`; its checks are a file scope and a size cap, so a person reads every change. `issue_label` and `dependency_update` crews (Run now has no event to start them with; their listener owns that), a `watch` crew (it runs its command on its schedule; its own `watch:<start>` event is accepted) and crews that are off are refused, and a start whose engine has spent the crew's daily budget is refused before anything is stored (PR 2, `background_daily`). The listeners (PR 3) fire the same start with their own event key. The service's `POST /api/crew/background/{id}/run-now` route (a Person route) calls the manual one. A waiting run's review is settled by the person's acknowledgement (`background_acknowledge_review`) |
| `triggers` | `.orbyn/crew.json` `background` triggers and templates, parsed and checked: kinds, budgets, engines, schedules, hidden text and name collisions. Pure policy: nothing starts, writes or calls a model |
| `settle` | Applies a judgement: pass, or retry, change of approach or stop; the budget stop for the brief's minutes or turns; the result for the lead; a worker's run ending |
| `resume` | `crew_resume`: the lead's resume of a held task (protocol `crew.resume`). One transaction moves a `needs_person` task whose worker reported back to `running`, then the worker is told to carry on through the same guarded path every retry uses, with the same thread, answer key and budget; a task whose worker never ran, one waiting on a person's `manual` check, a review lane, a merge correction, a busy worker and a task past its minutes are refused, and a prompt that cannot be queued puts the task back. A restart credits a held task its off time (`recover::excuse_held_downtime`), so the minutes it resumes with are not charged for the app being off. Not the person's cancel or answer, which stay theirs (docs/crew.md, "As built (resume)") |
| `stop` | `crew_stop`: the lead's stop of a task it leads (protocol `crew.stop`). One transaction moves the task to `stopped` with reason `lead_stopped`, then the same end a budget or repeated-failure stop takes releases its leases, requests its worker's run to stop and writes the final result. Only the task's own lead thread may call it (a worker's token and another crew are refused), and a final, `briefed` or `routed` task is refused. Not the person's cancel, which stays the only `cancelled` ending (docs/crew.md, "As built (lead stop)") |
| `dashboard` | The dashboard read (W12, row G18, [docs/crew-dashboard.md](../../../../docs/crew-dashboard.md)): one repository's figures for a 30, 60 or 90 day window from this device's own records, writing nothing, plus the KC3 `live` row that is not windowed: what waits for the person now from `crew_needs_you` (by kind, dismissals included) and the workers that own live work now from the one `working` function (by why), read in one bounded query of at most 500 workers with `truncated` when it cuts; Idle is not served because the store keeps no crew member without a task. Merges, the ones that needed nothing from the person (`unaided`, from the approval ledger and an answered engine question), reverts with who reverted them and whether the cause was certain, the cycle from the brief's `crew_tasks.created_at` to the merge, weeks counted from the person's local Monday (their `utc_offset_minutes`, as the daily digest takes it), engines and areas with their record, and a cost only in one engine's own unit from the merge's proof (never summed across units). A figure the records cannot measure is left out, never sent as `0`. Free text is redacted, has the task's answer-key text withheld and the person's Settings › Secrets patterns masked, and is capped at 200 characters. Its window, weeks, lists and refusals are in `tests/dashboard.rs` |
| `lessons` | Crew lessons (KC5 slices 1 and 2): the three sources the core learns from, all code-owned or the person's own words -- a repeated failure fingerprint (the loop guard's own hash, on two tasks of one repository within 60 days), a confirmed escape or revert (the escape log, once a person confirms; a person's own revert learns at once), and a person's correction. One short sentence (at most 300 characters) per lesson, scoped to one repository or global, with evidence ids only; a repository lesson may name a repo-relative path, a global one names path classes only. One write path: the secret scan refuses with its own sentence, a fingerprint already remembered is never rewritten, and at the cap (50 per repository, 20 global) the oldest least-used lesson is hidden, never deleted. Every lesson-content write audits first in the same transaction (rule 6); the brief's use and left-out counters audit nothing and run inside the transaction that stores the brief. Nothing is synced, and nothing here routes, verifies or changes a check. A start that sends the brief carries the repository's active lessons then the device's global ones, newest first, at most five and 1500 characters, wrapped as `<crew-lessons trust="data">` after the brief and outside the `Brief` object, so routing and the checks never read one; each lesson is secret-scanned again and checked against the task's key on the way in, a lesson the key check fails is left out of that one brief and counted in `left_out_of` (migration 81), a brief's uses and last use are counted in the transaction that stores it, and a per-repository "use lessons" switch (on by default, `project_preferences` key `crew_use_lessons`) stops injection without stopping learning. Stored by `store::crew_lessons` (migrations 80, 81, 84 and 85); slice 3 part 1 adds the person's list, detail, add by hand, edit, on/off, promote and demote, the 10 s delete and undo, and the per-repository switch, all behind Preview and audited; the routes come in part 2. A lesson that is a source of an approved skill proposal whose local skill still exists reads `skill` and leaves briefs (`in_next_brief` false) until that skill folder is removed, and its `rev` never changes for this. The task's recorded EvalHistory sample is read back by `Core::crew_task_samples` (KC5 slice 4 read; ids and enums only, `404 not_found` for an unknown task, and no row for a task stored before samples existed) |
| `proposals` | Skill proposals (KC9 part 1): when three or more active, visible, non-deleted lessons of one repository share a group key -- the source, the failing check kinds of a fingerprint lesson (`+`-joined, sorted and deduped) and the path area of a fingerprint failure or an escape -- the core makes one proposal from a fixed template over those lessons' own texts. No model is called, nothing leaves the device, a proposal blocks nothing and never reaches needs-you, and it is device-local and never synced. A person lesson has neither column and never groups. One proposal per (project, group key) ever: a dismissed or approved row stays, so the pattern is not proposed again even after its lessons are purged. ## EvalHistory samples

Each Crew task records exactly one EvalHistory sample (KC5 slice 4) in `store::crew_eval_samples` (migration 88): the
brief's kind, whether it carried lessons and those lesson ids, then its outcome, stop reason, latest routed engine and
finish time. The one outcome is written once, by the task's first final state, and a later move never overwrites it. A
task's sample is read back by `Core::crew_task_samples` behind Preview, class Local, as
`GET /api/crew/tasks/{id}/samples`: ids and enums only, `404 not_found` for an unknown task, and no row for a task
stored before samples existed. Reading a sample changes nothing: `EvalHistory` and `score` keep their exact shape,
every router caller still passes `EvalHistory::default()` (the read does not feed the router), and a test proves the
router's decision is identical with and without samples. The rows are device only, never synced or exported, and hold
ids and enums, never text.

## Rules to keep

- The router's inputs are the brief and this machine's own configuration. A brief has no
  field for the answer key, and no function here takes one except the leak check on storing.
- An engine or model the machine has not configured is never routed to. An explicit engine
  that fails a filter is refused with its reason, never swapped for another.
- Effort is `medium`, never higher. A review brief, the finding check and a second key are lead tier, and a named model below it is refused. A review lane is worker tier unless it is the `security` lane, a repo rule locks it, it is the merge-owed `correctness` lane or only the author's vendor can review it; a pinned model wins otherwise.
- Every rejection carries a reason, and a score carries its basis (`used_defaults`, or the
  measured rate with its sample size).
- No learning, trust score or counterfactual fork here: those are later slices, and
  `EvalHistory` is the one place they will feed in.
- Only the lead starts a task or routes (H3). A worker's thread is found by `crew_runs`, and its
  tools refuse once the run ends (H7); the core's own verification still adds Evidence and a Gate.
- The checks run when the worker's turn has ended, never during it, so the worker cannot change files
  while they run. Before any check, a change to a file in the key's protected paths fails the attempt
  with a reason that names no file (N7, H9, H11). The files are recorded at `crew_start` and compared
  byte for byte, never through git, so `.gitignore`, `update-index` flags, `.git/config`, replace refs, loose objects
  and alternates cannot hide an edit. Exactly one verification runs per task: it is claimed in the transaction.
- The verifier is code. A worker is told why a check failed (redacted, with the key's text
  withheld, then proven free of both) and never the check, its id or any other part of the key (H1).
- `failed` is never at rest: a failed verification goes through it to the state the loop guard
  names in one transaction. `final` is true only for `passed`, `stopped` and `cancelled`.
- The guard compares fingerprints: the failing checks, how each ended and the names of what
  failed (tests, or files outside the lease), never the output, which changes between runs. The same failure twice gives one change of approach; the same
  failure after that stops the run (`repeated_failure`).
- Messages and facts pass the secret scan and the answer-key check on the way in and out; a worker never sees the lead's
  thread or messages to others (see the [bus](bus/README.md)).
- A lease is read for expiry when it is used, never by a timer; a lapsed one is recorded `expired`
  once and blocks nobody. `crew_start` takes one lock, so two briefs cannot both be granted a path.
  A worker's file change is refused at the gate when it is outside the lease, with the lease's own words.
  The gate asks that check whether or not Autopilot's chain was bound, and a lease it cannot read is a
  refusal, not a pass.
- A crew-wide turn budget is one device-local number (`crew_turn_budget`, whole turns; 0 or unset is
  none), set in Settings › General. A crew's spend is the per-task tally summed over its tasks, so the two budgets cannot disagree; a new
  task is refused once the crew has spent it, and a task already running is never stopped by it. It fails closed: a budget or a
  spend that cannot be read refuses the start rather than reading as no budget.
- The lead's stop is the lead's own: only the thread that leads a task stops it, a worker's token or a task of
  another crew is refused, and a task that already ended or that the lifecycle cannot stop from `briefed` or `routed` is
  refused. A person's cancel stays the only `cancelled` ending.

## Stack budget

Tokio worker and test threads have 2 MiB stacks, and the check chain runs deep: forge watch ->
`prepare_and_verify_forge_correction` -> `verify_forge_correction` -> `crew_verify` -> `run_check`
-> `run_line`. Futures over 16 KiB are `Box::pin`ed at their await sites, and `tests/future_sizes.rs`
measures each and guards a budget with 25% headroom. Re-measure with
`cargo test -p orbyn-core --lib -- crew::tests::future_sizes --nocapture`.

## Known limits of Preview

- Background processes a worker starts outlive its turn. They can edit protected files after a check has read
  them, or read a check command from `ps`. Fixing it needs the worker's own worktree and killing its process
  group (#436).
- A worker runs as the same OS user, so its shell can read the Orbyn SQLite store (the answer-key table and the
  lead's thread) or call the `orbyn` CLI. No tool refusal can stop that; it needs a sandbox that blocks reads of
  the app data folder (#441).
- An attachment tool takes a thread id; a worker may name only its own. `computer_*` and every `orbyn_*` tool
  off the allow list are refused to a worker.
- A worker's shell command is not read, so it can still write outside its lease; the gate sees the engine's
  file-change tools, not files a command writes (#441).
- A key with protected paths and no record of them from the start fails closed (`needs_person`).

## Follow-ups

- Known gap: Evidence keeps the output's hash and a 4000-character redacted excerpt, not the full log.
- Evidence names HEAD as its commit; when the checkout had uncommitted changes, `does_not_prove` says so.
- `budget.minutes` ends a task even in the middle of a turn, through a timer that holds the core weakly and
  is set again after a restart. A verification gets what is left of the budget and stops once the task has
  been stopped. `budget.turns` stops the next failed attempt once the worker's turns and the approvals reserved
  against the same budget reach the brief's turns. A crew whose turn budget is spent starts no new task,
  and a task already running is not stopped by it. The check sits in `launch_crew_task`, so `crew_start`, background
  Run-now, escape checks, review lanes and fixes pass it. Autopilot's merge corrections (`autopilot/merge/correction.rs`)
  call `create_crew_task` directly and are not checked: they are deterministic and spend no worker turns. A task whose
  worker thread exists or whose first prompt is still queued counts at least one turn, so a queued start is not free.
- Windows: the leak test (`a_failing_check_that_prints_its_own_command_leaks_nothing_to_the_worker`) is
  Unix-only. On Windows a command's echo can differ in quotes and line endings, so the withholding needs its
  own test there, and a check's deadline must kill every process the check started (the process owner does;
  no Windows test shows it yet).
- The worker runs in the lead's checkout, as `delegate` does. A writing worker's own worktree
  (docs/crew.md, "Isolation") is not created yet, so the diff checks see the lead's changes too.
- The check kinds `preview`, `visual_compare`, `screenshot_only`, `accessibility_audit`,
  `performance_budget` and `licence_scan` are accepted limits (#793): each reports `skipped` and is listed as
  not verified, with the sentence that names what it needs and the decision it waits on, recorded in
  docs/crew.md, "Check kinds this version does not run". `schema`, `secret_scan`, `repo_required`,
  `http_probe` and `manual` run (docs/crew.md, "Verification without limits").
- Tier words match whole words in a model's id or label; they are defaults to check against real ids.

## How it is tested

Fake engines (`tests/fake.rs`) stand in for the registry, so each filter, each score, the
explicit override and the tool are checked with no process started. `tests/core.rs` runs the
tool through a real `Core` with a scripted engine driver. `tests/harness.rs` is a real `Core`
with a fake worker that writes files in a git checkout and calls `crew_report` over MCP: `runs.rs`
takes a task from its first turn to the end (fail, retry with the reason, the same failure twice,
one change of approach, stop; pass; no report; engine error), `starts.rs` covers what a start
refuses and the lease rules, `lead_stop.rs` the lead's stop and the tokens it refuses, `resume_held.rs` the lead's resume of a held task and the callers it
refuses, `lifecycle.rs` checks the table against the spec's own, and `verify.rs` the reason a worker may read and the check runners. `unrun_kinds.rs` holds a skipped kind to its accepted limit and to docs/crew.md, `http_probe.rs` runs probes against a loopback server it starts. `review.rs` runs the review stages (see the [review README](review/README.md)). `bus.rs` and `bus_guards.rs` run two fake engines (one
takes input mid-turn, one does not) through the [bus](bus/README.md).

The crate's [group table](../../README.md#groups) lists every group.
